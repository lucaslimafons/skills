Background

The app has a recipe wizard. Step 2 lets you edit one ingredient. Tapping the pencil on an ingredient row opens a bottom sheet: a panel that slides up from the bottom of the screen.

That sheet is IngredientFormSheet. It holds five fields. The first is Quantity, which is numeric, so tapping it opens the number pad. The second is Unit. Unit is not a text field. It is a button that opens a second bottom sheet, with one chip per unit.

So the app shows a sheet on top of a sheet. That is the whole setting for this bug.

New to bottom sheets in this app? Start here (skip if you know them)

The app uses a library called @gorhom/bottom-sheet, version 5.2.8. Three of its ideas matter here.

Detents. A sheet can stop at a few heights. Each stopping height is a detent. The library keeps them in an array, measured in points from the top of the screen. Code refers to a detent by its index in that array.

Dynamic sizing. With enableDynamicSizing, the sheet measures its own content and builds a single detent from it. So these sheets have an array of exactly one entry. The only valid indexes are 0 (open) and -1 (closed).

The modal stack. Sheets opened as BottomSheetModal register with a shared provider. The provider keeps a queue. When a new sheet opens, it decides what happens to the one already showing. That decision is the stackBehavior prop.

There is also keyboardBehavior. Set to "interactive", the sheet lifts itself as the keyboard opens, so the focused field stays visible above it. That lift is not a detent. It is a position the library computes on the fly.

Two earlier facts about this code are worth knowing, because the bug sits exactly between them.

First, the ingredient sheet uses keyboardShouldPersistTaps="handled" on its scroll view. That means tapping a button inside the sheet does not close the keyboard first. It was set so a tap on Save works on the first press instead of only dismissing the keyboard.

Second, an earlier commit already fixed a crash in these same sheets. It removed keyboardBlurBehavior="restore", because that setting made a sheet snap back to a stored index that was out of range. The error message in that commit is the same message in this one. This PR is the same fault reached by a different route.

The core idea

The library has one variable that is supposed to hold a detent index. In one situation it writes a position in points into that variable instead. The two are different kinds of number. Nothing checks the difference at the moment it is written.

Here is the situation. The keyboard is open, so the sheet sits at a lifted position. The library looks for that position in the detents array. It is not there, because the keyboard lift is not a detent. So it falls back to a number that is not an index.

On its own that bad number is harmless. It only gets read if something asks the sheet to go back to where it was. Opening the unit picker is exactly that something.

By default, opening a sheet over another sheet minimizes the one below: it slides down, and the library remembers which index to restore it to. It remembers 300.5. When the unit picker closes, it asks the ingredient sheet to go back to index 300.5. The sheet has one detent. The library checks the range, finds the number impossible, and throws.

One cause, two symptoms

The keyboard never closing is not a separate bug sitting next to the crash. It is the same fact. The keyboard being up is what makes the index bad, and it is also what hides the unit list. Fix the stack and the crash goes. Fix the keyboard and the list is visible. You need both, for reasons the walkthrough reaches in Fix 2.

Walking the code

This follows the fault, not the file order. The two fixed lines come late, because they only make sense once you have seen what they prevent.

2. Where the bad number comes from

When the sheet settles, the library works out which index it landed on. It looks up the position in the detents array. If the keyboard is open, the lifted position is not in that array, so the lookup fails and this fallback runs.

node_modules/@gorhom/bottom-sheet/src/components/bottomSheet/BottomSheet.tsx:653–663

/**
 * because keyboard position is not part of the detents array,
 * we will need to manually set the index to the highest detent index.
 */
if (
  index === -1 &&
  status === KEYBOARD_STATUS.SHOWN &&
  position !== closedDetentPosition
) {
  index = highestDetentPosition ?? DEFAULT_KEYBOARD_INDEX;
}
Read the comment against the code

The comment says "the highest detent index". The code assigns highestDetentPosition, which is a position in points. For a one-detent sheet the index should be 0 and the position is something like 300.5. This looks like a genuine bug in the library, not a thing the app is holding wrong. See Open questions.

3. Who stores the bad number

Opening a sheet goes through a shared provider. It looks at whatever sheet is currently on top and applies the stackBehavior of the incoming one. The default is "switch".

node_modules/@gorhom/bottom-sheet/src/components/bottomSheetModalProvider/BottomSheetModalProvider.tsx:71–75

if (stackBehavior === MODAL_STACK_BEHAVIOR.replace) {
  currentMountedSheet.ref?.current?.dismiss();
} else if (stackBehavior === MODAL_STACK_BEHAVIOR.switch) {
  currentMountedSheet.ref?.current?.minimize();
}

minimize() slides the ingredient sheet out of the way and saves the index to come back to. The index it saves is the one the sheet last reported, which is now 300.5.

node_modules/@gorhom/bottom-sheet/src/components/bottomSheetModal/BottomSheetModal.tsx:274–286

minimized.current = true;

/**
 * if modal got minimized before it finish its mounting
 * animation, we set the `restoreIndexRef` to the
 * provided index.
 */
if (currentIndexRef.current === -1) {
  restoreIndexRef.current = index;
} else {
  restoreIndexRef.current = currentIndexRef.current;
}
bottomSheetRef.current?.close();

4. Where it blows up

Closing the unit picker tells the provider to restore the sheet underneath. That calls handleRestore, which hands the stored number straight to snapToIndex.

node_modules/@gorhom/bottom-sheet/src/components/bottomSheetModal/BottomSheetModal.tsx:302–306

if (!minimized.current || forcedDismissed.current) {
  return;
}
minimized.current = false;
bottomSheetRef.current?.snapToIndex(restoreIndexRef.current);

And snapToIndex range-checks its argument. With one detent, detents.length - 1 is 0.

node_modules/@gorhom/bottom-sheet/src/components/bottomSheet/BottomSheet.tsx:1090–1095

invariant(
  index >= -1 && index <= detents.length - 1,
  `'index' was provided but out of the provided snap points range! expected value to be between -1, ${
    detents.length - 1
  }`
);

That is the message seen on the device: 'index' was provided but out of the provided snap points range! expected value to be between -1, 0. An invariant throws. Nothing catches it, so the app goes down.

Edge case worth noting

Selecting a unit is not the only trigger. Tapping the dimmed backdrop closes the picker through the same path, and crashes the same way. The original report said "select any unit" because that is what a user would naturally do.

5. Fix 1: do not minimize the sheet below

The first change is one prop on the picker's own sheet.

src/components/forms/UnitPicker.tsx:122–126

<BottomSheetModal
  ref={sheetRef}
  enableDynamicSizing
  stackBehavior="push"

With "push", the provider skips the minimize() call in step 3. The ingredient sheet stays where it is and the picker draws over it.

The restore call still happens when the picker closes — the provider makes it regardless of stack behavior. But look again at the guard at the top of handleRestore in step 4: if (!minimized.current ...) return;. The sheet was never minimized, so minimized.current is still false, and the function returns before reaching snapToIndex. The bad number is never read.

6. Fix 2: close the keyboard

The second change closes the number pad when the picker opens.

src/components/forms/UnitPicker.tsx:56–63

// The picker lives inside the ingredient sheet, whose quantity field opens a
// number pad. That keyboard belongs to a TextInput in a sheet that stays
// mounted, so nothing blurs it on its own: it would sit on top of the unit
// list and hide every option.
const openSheet = useCallback(() => {
  Keyboard.dismiss();
  sheetRef.current?.present();
}, []);

Why does nothing else close it? Two reasons stack up. The scroll view uses keyboardShouldPersistTaps="handled", so a tap on the Unit button does not blur the field. And the picker is not a native modal, it is a sibling view in the same tree, so opening it never moves focus. The field stays focused and the keyboard stays up.

Why both fixes, not just this one

It is tempting to think closing the keyboard is enough, since a closed keyboard means a valid index. It is not. present() defers its work to requestAnimationFrame, so the stack is evaluated on the next frame, around 16 ms later. The keyboard takes roughly 250 ms to animate away. The index is still 300.5 when minimize() reads it.

So Keyboard.dismiss() fixes what the user sees, and stackBehavior="push" fixes the crash. Neither covers for the other.

7. The i18n pass, and the bug it uncovered

The project rule is that every user-facing string goes through t(), with a key in all three locale files. The three sheets the wizard opens had no t() calls at all. Everything in them shipped in English to Spanish and Brazilian Portuguese users.

The second commit adds 19 keys per locale and routes the labels through them. Save and Delete reuse the existing common.save and common.delete.

Unit chips are the interesting part. The picker used to build its own English labels.

src/components/forms/UnitPicker.tsx — removed

function formatUnitLabel(unit: MeasurementUnit): string {
  if (unit === 'to_taste') return 'To taste';
  return unit.charAt(0).toUpperCase() + unit.slice(1);
}

There was already a shared helper doing this properly, used by the shopping list and by ingredient rows. The picker now calls it instead, so a unit reads the same everywhere.

src/features/recipes/unitConversion.ts:94–96

export function unitLabel(unit: MeasurementUnit): string {
  return t(`shopping_list.units.${unit}`);
}

Switching to it exposed a separate live bug. The shopping_list.units catalog had 15 entries, but MeasurementUnit has 16 values. whole was missing. The picker had been hiding that behind its own formatter, which happily produced "Whole" from the enum value. Every other caller of unitLabel — shopping list, ingredient rows, the nutrition basis sheet — was rendering a missing-key message for that unit. The key is now added in all three locales.

A visible side effect

Chips now read g and to taste instead of G and To taste. The title case came from capitalizing the enum value. Spanish and Portuguese do not title case units, so the shared catalog does not either.

8. A rename that prevents a future bug

The third commit is two words. Both numeric fields named their callback argument t, which now shadows the t imported for translations in the same file.

src/features/recipes/IngredientFormSheet.tsx:209

- onChangeText={(t) => onChange((t ?? '').replace(/[^0-9]/g, ''))}
+ onChangeText={(text) => onChange((text ?? '').replace(/[^0-9]/g, ''))}

Nothing was broken. The shadow is a string and these call sites do not need the catalog. But the next person to add a label inside that callback would get t is not a function at runtime, with nothing in the diff to explain why. The same line exists in StepFormSheet.tsx:232 and changed too.

9. The tests

The crash lives in the library's animation layer, which Jest cannot run here: the project stubs out Reanimated. So the tests guard the contract instead — the two properties that, if either regressed, would bring the bug back.

src/components/forms/__tests__/UnitPicker.test.tsx:65–75

it('stacks with "push" so the sheet underneath is never minimized', () => {
  render(<UnitPicker value={null} onChange={jest.fn()} />);

  expect(mockSheetRender).toHaveBeenCalledWith(
    expect.objectContaining({ stackBehavior: 'push' }),
  );
});

stackBehavior renders nothing, so there is no DOM to assert on. The mock sheet reports the props it received to a jest.fn(), and the test inspects that call.

The gate was proven, not assumed

A regression test only counts as evidence if it fails on the broken code. Both fixes were removed, the suite was run, and the two guard tests failed. The fixes were restored and they passed again. The rest of the suite is 167 files and 1517 tests, all passing.

Open questions

The library fault is still there, and it is known upstream. This PR routes around the fault; it does not fix it. Any future sheet opened over a form sheet that holds a keyboard can hit the same invariant. The rule is in docs/AI_CORE_CONTEXT.md so the next person finds it, but nothing enforces it mechanically.

An earlier version of this section said nothing had been filed upstream. That was not checked, and it was wrong. Two issues carry this exact error message, both reporting a bottom sheet opened inside another bottom sheet:

  • gorhom/react-native-bottom-sheet#2648 — closed automatically by a bot for not following the issue template.
  • gorhom/react-native-bottom-sheet#2649 — closed automatically as stale after 30 days with no reply.

Neither was triaged by a maintainer. A later comment on #2649, from a user on the same version this app uses, gives a production stack trace that matches the path traced in this document line for line, ending at BottomSheetModal.tsx:306.

Two routes, one broken line

That reporter blames a different cause: a sheet whose detents shrank from two to one while another modal sat on top. This app's trigger is the keyboard instead. Both end at the same line, because restoreIndexRef is captured at minimize time and never re-checked against the detents that exist at restore time. That is why stackBehavior="push" is the right fix rather than sanitizing the number: it removes the restore path instead of guarding one way of poisoning it.

The stack trace is corroboration, not authority. It is a comment from a stranger, and their causal explanation is theirs, not something verified here.

The sheet stays at keyboard height. After the keyboard closes, the ingredient sheet keeps its lifted height instead of settling back to fit its content. That is pre-existing — it reproduces with the picker entirely out of the picture — and it is the deliberate cost of an earlier commit dropping keyboardBlurBehavior="restore". The obvious fix is the exact setting that caused the earlier crash, so it was left for its own change.

Validation messages: fixed, after this page first said otherwise. An earlier version of this section said the Zod messages were left in English because fixing them needed a new app-wide pattern. That was wrong twice over, and a fourth commit fixes them.

It was wrong because the codebase already called t() inside schemas — src/features/auth/schemas.ts and src/schemas/common.ts had done so from the start — so plain English in the recipe schemas was an omission, not consistency. And because this project is on Zod 4, where the error option accepts a function that runs at validation time, so nothing had to be invented.

The half that was true is sharper than it looked. An eager t() in a schema is itself a bug, and auth/schemas.ts had it. Schemas are module-level constants, evaluated once on import, so the message freezes at whatever locale was active then. src/features/preferences/useApplyPreferredLocale.ts:21 assigns i18n.locale long after import, when the user picks a language in preferences. The frozen message does not follow. Every message now takes the lazy form:

src/features/recipes/schemas.ts:160–162

ingredientName: z
  .string()
  .min(1, { error: () => t('errors.ingredient_name_required') }),

src/lib/env.ts keeps its English messages on purpose. Those validate environment variables at startup and are read by whoever runs the build, never by a user.

Only English was checked on a device. The Spanish and Brazilian Portuguese strings were written for this PR and are enforced for key parity by pnpm i18n:check, but nobody has run the app in those locales to see the sheets. Wording and truncation are unverified.
